# 第四步：渠道与月份的可见签约指标

## 先固定指标定义

已观察签约占比＝发布文件内匹配到签约记录的MQL数÷该组全部MQL记录数。统计单位是线索记录，不是消费者订单或已验证的独立商家。

观察范围是这批文件中的全部可见签约记录；没有把今天或最大签约日期当作统一随访截止，也没有承诺所有线索都被完整跟踪相同时长。本表是描述性快照，不是最终签约率或渠道因果效果。

整体：8,000条线索，842条匹配签约，7,158条未匹配；已观察签约占比10.53%。

日期冲突1条仍保留在分母与匹配签约计数中，并单独标记。此步不计算签约时长。

## 实际执行的两条SQL

### 04_channel_metrics.sql

```sql
-- 第四步：各来源在发布文件内的可见签约情况。
-- 口径：匹配到签约记录的MQL数 / 该来源全部MQL记录数。
-- 这是记录内可见签约占比，不是最终签约率，也不是渠道因果效果。
-- 保留空来源、unknown、未匹配签约及日期冲突记录。

SELECT
    origin_group AS channel,
    COUNT(*) AS lead_count,
    SUM(has_observed_won) AS observed_won_count,
    SUM(1 - has_observed_won) AS unmatched_won_count,
    100.0 * SUM(has_observed_won) / COUNT(*) AS observed_won_pct,
    SUM(date_order_issue) AS date_issue_count
FROM lead_overview
GROUP BY origin_group
ORDER BY lead_count DESC, channel ASC;
```

### 04_channel_month_metrics.sql

```sql
-- 按首次联系月份与来源同时分组，便于后续查看月份构成差异。
-- 此表只包含有线索的组合；没有线索的组合不补成0%签约占比。
-- 签约记录可以晚于首次联系月份；这里不是统计每月发生的签约数。

SELECT
    first_contact_month AS contact_month,
    origin_group AS channel,
    COUNT(*) AS lead_count,
    SUM(has_observed_won) AS observed_won_count,
    SUM(1 - has_observed_won) AS unmatched_won_count,
    100.0 * SUM(has_observed_won) / COUNT(*) AS observed_won_pct,
    SUM(date_order_issue) AS date_issue_count
FROM lead_overview
GROUP BY first_contact_month, origin_group
ORDER BY contact_month ASC, lead_count DESC, channel ASC;
```

## 本步SQL怎么读

- COUNT(*)：该组有多少条线索。
- SUM(has_observed_won)：把匹配标志的1相加，得到匹配签约的线索数。
- 100.0 * SUM(has_observed_won) / COUNT(*)：计算百分比；100.0保留小数运算。
- GROUP BY first_contact_month, origin_group：同时按月份和来源分组。

## 先回答三个业务问题

1. 自然搜索和付费搜索，哪个线索更多？哪个已观察签约占比更高？
2. 为什么不能因为空来源的占比高，就建议给它追加预算？
3. 若两个渠道进入的月份构成不同，直接比较整体占比可能遗漏什么？

下一步再讨论月份构成、可见签约记录的时间分布与观察窗口限制。本表尚未校正这些差异，也未完成成本、ROI或预算优化分析。
